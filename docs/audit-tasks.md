Источник: [docs/audit-2026-08-08.md](audit-2026-08-08.md). Порядок — от «ущерб / размер фикса»
к косметике. Волны независимы между собой; внутри волны задачи можно брать параллельно, кроме
явно отмеченных зависимостей.

Базовая линия: `ruff check .` → 14 (все в `tests/`), `pytest -q` → 324 passed.
Каждая задача считается закрытой, только когда есть **запускаемая проверка** (тест или assert),
падающая до фикса.

## Волна 0 — потеря данных и порча состояния (делать первой)

- [ ] **T-01. Reaper зависших `sending`** — `core/state/posts.py:503`, `core/migrate.py` / старт
  `main.py`.
  Краш между `claim_post_for_sending` и `mark_*` вешает пост навсегда: невидим для
  `list_due_posts` (`:492`), неотменяем (`:460`), вечно занимает квоту (`:17`).
  **Фикс:** при старте `UPDATE scheduled_posts SET status='pending' WHERE status='sending'`.
  Решить: возвращать все сразу или только «старше N» (второе требует колонки `claimed_at` →
  миграция; для одного процесса достаточно первого).
  **Проверка:** тест — оставить пост в `sending`, выполнить старт-путь, убедиться, что он снова
  виден в `list_due_posts` и не занимает квоту.

- [ ] **T-02. Сериализация записей в единственное соединение** — `core/db.py:6`,
  `core/state/base.py`.
  Воспроизведено: 27 `OperationalError: cannot start a transaction within a transaction` на 80
  вызовов из 5 корутин; чужой `commit()` внутри открытой транзакции переживает `rollback()`.
  8 сайтов `BEGIN IMMEDIATE`: `posts.py:283`, `recurring.py:189/267/368`, `drafts.py:93/291`,
  `teams.py:13/205`.
  **Фикс:** один `asyncio.Lock` в `StateStoreBase`, удерживаемый на всех методах записи.
  Пометить `ponytail:` — потолок «глобальный лок», апгрейд «отдельное соединение на воркер».
  **Проверка:** `asyncio.gather` конкурентных `create_*` + отмена; ноль `OperationalError`,
  rollback одного не роняет данные другого.

- [ ] **T-03. Залп после простоя** — `core/scheduler.py:96`.
  Воспроизведено: daily-паттерн, простой 3 суток → 4 поста за 4 тика (~8 c).
  **Фикс:** прокручивать `calculate_next_occurrence` в цикле, пока результат `<= now`, до
  материализации. Учесть взаимодействие с `max_occurrences` (пропущенные вхождения — считать или
  нет; предлагаемое решение: считать, серия не должна растягиваться простоем).
  **Проверка:** инстанс с `scheduled_for_utc` месячной давности → ровно одна материализация в
  будущем, не 30 отправок.

- [ ] **T-04. Обход лимита активных постов повторами** — `core/state/recurring.py:363` и `:277`.
  `create_recurring_series` зовёт только `_guard_recurring_cap`; `materialize_next_recurring_post`
  не зовёт ничего, при этом обе пишут в `scheduled_posts`.
  **Фикс:** `await self._guard_active_posts_cap(user_id)` в обеих.
  **Проверка:** monkeypatch лимита в 2, третья материализация → `ResourceLimitError`.

- [ ] **T-05. Атомарность `mark_sent` + материализации** — `core/scheduler.py:177-181`.
  Краш между двумя транзакциями обрывает серию навсегда и молча; repair-пути нет,
  `recurring.py:454 get_due_recurring_instances` вызывается только из тестов.
  **Фикс (выбрать):** (а) слить в одну транзакцию, либо (б) backfill на старте по уже
  существующему `get_due_recurring_instances` — тогда мёртвый метод оживает вместо удаления.
  Зависит от **T-02** (лок).
  **Проверка:** пометить пост `sent` без материализации → после старт-пути активный паттерн снова
  имеет pending-инстанс.

- [ ] **T-06. Кирпич миграций на baseline** — `core/migrate.py:46`.
  Воспроизведено: БД с таблицами только 001+003 штампуется `[1..5]`, `base.py:41` падает на
  `no such table: team_members`, рестарт пропускает все файлы.
  **Фикс:** baseline только когда присутствуют **все** таблицы, создаваемые миграциями.
  **Проверка:** тест на частичную схему → миграции доезжают, не штампуются вхолостую.

  **Фикс:** детектить `utcoffset(fold=0) != utcoffset(fold=1)` и либо явно сообщать о сдвиге, либо

  **Проверка:** тест на дату перехода.

- [ ] **T-12. Потеря сообщений при flood-wait в рассылке** —
  `core/services/admin_broadcast_svc.py:53`.
  `except Exception` без разбора `TelegramRetryAfter` (в `scheduler.py:183` разбор есть) →
  сообщения считаются `failed` и теряются без повтора.
