# Аудит auto-sender-bot — 2026-08-08

Полный аудит кодовой базы (режим ponytail full). Пять параллельных треков: время/планировщик,
состояние/БД, Telegram-поверхность, web/вход-выход/lifecycle, слой services + тесты.
Спорные пункты между треками разобраны отдельно (см. «Арбитраж»).

**База прогона:** `ruff check .` → 14 нарушений, все в `tests/`; `core/` и `telegram/` чистые.
`pytest -q` → **324 passed** (`.venv/bin/pytest` не существует, прогон системным pytest).
Все находки получены на зелёном дереве. Код не менялся.

**Воспроизведены скриптами:** конкурентные транзакции (27 `OperationalError` на 80 вызовов),
catch-up-залп (4 поста за 4 тика), кирпич миграций, DST-сдвиг «1 час».
**Воспроизведены прогоном апдейтов через `Dispatcher`:** проглатывание команд в FSM-состояниях,
утечка состояния в группе, перескок флоу по устаревшей кнопке.

## 1. Фактическая архитектура

```
main.py: один conn (aiosqlite, WAL) → StateStore → раздаётся 4 конкурентным потребителям
  ├─ Dispatcher.start_polling ──→ telegram/router.py (8 суб-роутеров, shared первый)
  │                                  └─ handlers/* → core/services/* → StateStore
  ├─ scheduler_loop (свой poll 2 c) → list_due_posts(10) → claim → notifier → mark_*
  ├─ healthcheck :8080 (единственный наблюдатель за scheduler_task)
  └─ webapp :8081 (aiohttp) → initData HMAC → StateStore напрямую, мимо services
```

- `shared.py` (1142) — не «утилиты», а один роутер, держащий datetime-picker, сбор медиа и
  подтверждение **для всех пяти флоу** (Schedule/Repeat/Draft/Broadcast/Edit). Размер = одна и та же
  5-веточная диспетчеризация по `current_state`, написанная 3 раза, и одна и та же таблица
  переходов — 3 раза.
- `helpers.py` (897) / `keyboards.py` (616) — граница между ними не «хелперы/клавиатуры», а
  **async-vs-sync**: поэтому форматирование текста и парсеры токенов живут в `keyboards.py`.
- `core/services/*` (261 строка) — оправдан на 6 функций из 8 (изоляция ошибок рассылки, RBAC-гейт
  черновиков, резолв назначений). Не anemic-слой, сносить целиком не за что.
- Повтор материализуется **не** отдельным циклом: `get_due_recurring_instances` в проде не
  вызывается вообще, серия движется через `list_due_posts` → после `mark_sent` отдельной транзакцией.
- Mini App ходит в `StateStore` в обход `services` — отсюда расхождение двух поверхностей.
- `StateStore` = `StateStoreBase` + 8 миксинов, один сайт инстанцирования (`main.py:31`),
  63 кросс-миксиновых `self.`-вызова. Разделения по факту нет.

## 6. Арбитраж спорных пунктов между треками

- **Потеря entities при разбиении (`core/notifier.py:37`, `:65`)** — два трека назвали багом, один
  пометил как требующее проверки. Проверено самостоятельно: ветка при превышении лимита
  **недостижима**. `scheduled_posts.text` пишется только из `message.text` (`shared.py:589`,
  `queue.py:579`) и из `/api/broadcast` с отсечкой 4096 (`webapp.py:369`); лимит Telegram считается
  в UTF-16 единицах, которых всегда ≥ кодпоинтов, поэтому `len(text) > 4096` не наступает.
  То же для `caption > 1024`. Классификация: **risk (латентная ловушка + мёртвая ветка)**, не bug.
  Удалять строку 37 нельзя — она же обслуживает нормальный путь «пост без форматирования».
- **UTF-16 переполнение (`'😀'*3000` проходит проверку `<= 4096`)** — **опровергнуто**: направление
  обратное. UTF-16-длина ≥ длины в кодпоинтах, поэтому текст, который Telegram принял от юзера,
  гарантированно укладывается и в проверку по кодпоинтам.
- **Несогласованность DST между тремя путями** — исходная гипотеза задачи **не подтвердилась**
  (см. раздел 5). Реальные проблемы рядом: ложное отображение времени юзеру (`utils.py:55`),
  «1 час» по стенным часам (`time_picker.py:80`), фиксация сдвинутого `time_of_day_minutes`
  для всей серии (`shared.py:954`).
- **`ruff check .`** — треки называли 14 и 19; перепроверено: **14**, все в `tests/`.
