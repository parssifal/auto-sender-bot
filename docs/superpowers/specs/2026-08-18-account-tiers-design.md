## Цель

Ввести уровни аккаунтов **basic / pro / premium**. Более высокий уровень даёт:
увеличенные лимиты (посты, каналы, черновики, recurring), реакции-затравки на
публикуемых постах (1→3 эмодзи по тарифу, пресеты по типу поста), и рефералку с
бонусом обоим участникам. Оплата — вне скоупа, помечается `# TODO` и выдаётся
руками через админку.

Решения пользователя (2026-08-18):
- Реферальный бонус получают **оба** — и пригласивший, и приглашённый.
- Реакции делаем **как задумано** (гейт 1→3 по тарифу, пресеты), но перед
  реализацией — отдельный шаг валидации Telegram Bot API.
- Сейчас — только уточнённый план, без кода.

## Затрагиваемые точки в коде (уже проверено)

- `core/limits.py` — глобальные `MAX_*`, читаются как атрибуты модуля в choke-points
  `core/state/{posts,drafts,destinations,recurring}.py`. Единственное место
  enforcement — сюда вешаем лимиты по тарифу.
- `core/notifier.py` — `send_text` / `send_media_post` уже возвращают
  `SendStats.message_ids`, но они нигде не сохраняются. Для реакций их нужно
  начать сохранять на пост.
- `core/scheduler.py:274-289` (`_process_due_post`) — место, где пост уходит в
  Telegram; после успешной отправки вешаем реакции.
- `telegram/handlers/shared.py:193-216` (`cmd_start`) — уже разбирает
  `?start=ti_<token>` (тим-инвайты). Рефералку добавляем веткой `ref_<id>` там же.
- `telegram/handlers/teams.py:109` — образец построения `?start=` deep-link.
- Админка: `core/webapp.py` (`api_user` / `api_users`, роуты `/api/user/{id}`),
  статик `core/webapp_static/admin.html`.
- Миграции: `core/migrate.py`, версионные файлы `core/migrations/NNN_*.sql`,
  применяются по порядку в одной транзакции.

## 1. Тарифная модель

Минимум, который работает: одна колонка на `users`, без отдельной таблицы
подписок (её заводим только когда появится оплата — YAGNI).

```sql
-- 009_plans.sql
ALTER TABLE users ADD COLUMN plan TEXT NOT NULL DEFAULT 'basic';  -- basic|pro|premium
ALTER TABLE users ADD COLUMN plan_expires_at INTEGER NULL;         -- NULL = бессрочно
```

Резолв «эффективного» тарифа — одна функция: если `plan_expires_at` в прошлом →
считаем `basic` (без фонового джоба; ленивая проверка на чтении).

Лимиты — dict в `core/limits.py` вместо голых констант:

```python
PLAN_LIMITS = {
    "basic":   {"posts": 50,  "destinations": 3,  "drafts": 20,  "recurring": 5,  "reactions": 1},
    "pro":     {"posts": 200, "destinations": 15, "drafts": 100, "recurring": 30, "reactions": 2},
    "premium": {"posts": 500, "destinations": 50, "drafts": 300, "recurring": 100,"reactions": 3},
}
def limit_for(plan: str, resource: str) -> int: ...
```

Числа — **открытый вопрос на тюнинг** (см. в конце). `basic` намеренно ужат по
каналам (3) — это главный апселл.

Enforcement: choke-points в `core/state/*` уже читают `limits.MAX_X`. Меняем на
резолв плана пользователя + `limit_for(plan, resource)`. Плата — один SELECT
плана на операцию создания (кэшируется в рамках операции). `ResourceLimitError`
и обработчики в хендлерах остаются как есть — сообщение об исчерпании лимита уже
локализовано, добавляем в него намёк на апгрейд тарифа.

## 2. Реакции-затравки

### Проверка платформы (сделать ДО реализации)

- Бот постит в канал → `bot.set_message_reaction(chat_id, message_id, reaction=[...])`
  на своём же сообщении. Реакция отображается **от имени канала/бота**, счётчик
  каждого эмодзи = **1** («затравка», не N живых реакций). Психологический эффект
  (на посте уже стоят эмоции → проще среагировать) достигается; накрутки чисел нет.
- Валидировать на реальном канале: (а) сколько эмодзи бот может выставить одним
  вызовом — от этого зависит гейт «1→3»; (б) что выбранные эмодзи входят в
  `available_reactions` канала (иначе API отклонит).
- `message_ids` уже возвращаются из `notifier`; начать сохранять их на пост,
  иначе реакцию вешать не на что.

### Модель данных

```sql
-- 010_reactions.sql
ALTER TABLE scheduled_posts ADD COLUMN post_type TEXT NULL;            -- 'happy'|'sad'|... (типизация)
ALTER TABLE scheduled_posts ADD COLUMN reaction_emojis_json TEXT NULL; -- какие эмодзи сеять

CREATE TABLE IF NOT EXISTS reaction_presets (
    id TEXT PRIMARY KEY,
    user_id INTEGER NOT NULL,
    name TEXT NOT NULL,
    post_type TEXT NULL,
    emojis_json TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    FOREIGN KEY (user_id) REFERENCES users(user_id) ON DELETE CASCADE
);

-- для реакций после отправки нужны message_id-ы отправленных сообщений:
CREATE TABLE IF NOT EXISTS scheduled_post_messages (
    post_id TEXT NOT NULL,
    message_id INTEGER NOT NULL,
    PRIMARY KEY (post_id, message_id),
    FOREIGN KEY (post_id) REFERENCES scheduled_posts(id) ON DELETE CASCADE
);
```

### Поток

1. При создании поста пользователь опционально выбирает тип поста и/или пресет →
   `reaction_emojis_json` (ограничен `limit_for(plan, "reactions")` по количеству).
2. `_process_due_post`: после успешной отправки сохраняем `message_ids`, затем на
   первое сообщение вешаем реакции. Ошибку реакции **не** считаем провалом поста
   (пост уже доставлен) — логируем и идём дальше.
3. Гейты по тарифу: basic — 1 эмодзи, без пресетов; pro — 2 + пресеты; premium —
   3 + расширенная палитра эмодзи по умолчанию.

Пресеты (весёлый/грустный набор) переиспользуются между постами; выбор типа поста
подтягивает соответствующий пресет.

## 3. Рефералы (бонус обоим)

`users.referred_by INTEGER NULL`.

Deep-link `https://t.me/<bot>?start=ref_<referrer_id>` (строится по образцу
`teams.py:109`). В `cmd_start` — ветка `ref_` рядом с `ti_`.

Anti-abuse (обязательно, т.к. бонус обоим — самый уязвимый вариант):
- Реферер пишется **только один раз**, при первом `/start`, если `referred_by`
  ещё NULL и пользователь только что создан.
- Нельзя пригласить самого себя (`referrer_id != new_user_id`).
- Реферер должен существовать в `users`.
- Бонус начисляется **не по `/start`, а по «активации»** приглашённого —
  квалифицирующее действие (первый привязанный канал ИЛИ первый запланированный
  пост). Это отсекает фейковые аккаунты, которые просто нажали `/start`.
- При активации: обоим — `+N дней Pro` (продление `plan_expires_at`, не понижая
  уже действующий premium). Флаг «бонус выдан» на приглашённом, чтобы не начислять
  повторно.

`N` дней и опциональный потолок суммарного бонуса — открытый вопрос на тюнинг.

## 4. Админка

- `api_user` (детально по пользователю): добавить `plan`, `plan_expires_at`, кем
  приглашён, скольких пригласил, сколько активировалось.
- Новый `POST /api/user/{id}/plan` — выдать/снять тариф и срок (только для админов,
  через существующий `_require_admin`).
- Блок в `admin.html`: текущий тариф, срок, кнопки выдать basic/pro/premium + поле
  «дней».
- Опционально bot-команда `/grant <id> <plan> [days]` как fallback — веб-панели
  достаточно, делаем только если попросят.
